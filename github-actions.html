Cách sử dụng tài liệu

Mục tiêu của tài liệu là giúp bạn tự thiết kế, đọc hiểu và vận hành một pipeline GitHub Actions phục vụ CI ứng dụng và triển khai hạ tầng bằng Terraform. Sau khi học, bạn cần trả lời được ba câu hỏi cho mỗi workflow: nó chạy khi nào, nó được phép làm gì, và bằng chứng nào cho thấy thay đổi đã được kiểm tra và triển khai đúng.

Ví dụ xuyên suốt dùng GitHub.com, runner Ubuntu do GitHub cung cấp và AWS. Các nguyên tắc về tách quyền, quản lý state, duyệt thay đổi và truy vết cũng áp dụng khi chuyển sang Azure hoặc Google Cloud; phần xác thực và quyền cloud phải thay tương ứng. Không có một bộ YAML duy nhất phù hợp mọi doanh nghiệp. Workflow tốt phải khớp với ranh giới tin cậy, mức rủi ro và cách vận hành của đội ngũ.

Bạn nên biết Git cơ bản, pull request, dòng lệnh Linux và khái niệm resource của Terraform. Nếu chưa quen Terraform, hãy đọc chương 9 trước khi làm lab. Học theo thứ tự chương 1 đến 8 để hiểu Actions; chương 9 đến 16 để xây luồng hạ tầng; chương 17 trở đi để vận hành và luyện tập.

Quy ước ví dụ. Các tag action như @v7 giúp đọc dễ hơn và phản ánh README chính thức lúc đối chiếu. Trước khi dùng production, thay bằng commit SHA đầy đủ đã xác minh, kiểm tra bản phát hành và cập nhật có review. Terraform CLI được cố định ở 1.14.6 làm mốc cho bài lab, không có nghĩa đây luôn là bản mới nhất. Các phiên bản action, runner và Terraform CLI là ba thứ độc lập. [G16–G20]

Phạm vi kiểm chứng. Workflow mẫu là cấu hình tham chiếu có điều kiện thiết lập, không phải cam kết triển khai được trên mọi tài khoản. Cần kiểm thử trong AWS sandbox của bạn, xác minh IAM, tính năng environment của gói GitHub và phiên bản action trước khi áp dụng thực tế. Bộ mã không chứa credentials, state thật hay provider lockfile giả.

1 Vai trò của GitHub Actions trong DevOps

GitHub Actions là nền tảng tự động hóa dựa trên sự kiện trong repository. Khi có sự kiện, GitHub chọn workflow phù hợp, tạo job và phân công runner thực thi. Một pipeline có thể kiểm tra code, chạy test, đóng gói, đăng nhập cloud, tạo Terraform plan hoặc triển khai ứng dụng. Bạn lưu logic trong Git để thay đổi pipeline cũng đi qua review. [G1]

Trong công việc hàng ngày, CI trả lời câu hỏi “thay đổi này có đạt các điều kiện tích hợp không”. Ví dụ, một pull request phải build được, test thành công và không vi phạm quy tắc chất lượng. Continuous delivery giữ hệ thống ở trạng thái có thể triển khai, thường có bước phê duyệt. Continuous deployment tự động đưa thay đổi đủ điều kiện lên môi trường đích. Đội của bạn cần thống nhất cách dùng hai nghĩa CD thay vì suy ra từ tên workflow.

Đối với Terraform, CI thường gồm format, khởi tạo provider, validate và kiểm tra policy. Chạy terraform apply đã là thao tác triển khai có thể sửa hoặc xóa hạ tầng. Vì vậy, một workflow CI xanh chưa đủ để cho phép apply. Bạn còn cần xác định account, state, người duyệt, quyền cloud và cách xử lý khi chạy dang dở.

Ví dụ thực tế: bạn mở pull request để bật versioning cho bucket. CI kiểm tra cấu hình, reviewer xem tác động và merge. Workflow trên main tạo plan mới dựa trên state hiện tại; người phụ trách xem plan của lần chạy đó rồi duyệt apply. Bằng chứng triển khai gồm commit SHA, workflow run, artifact plan, danh tính duyệt và log cloud. Đây là chuỗi kiểm soát thay đổi mà DevOps engineer phải thiết kế.

2 Mô hình thực thi và ranh giới dữ liệu

Thành phần Ý nghĩa Ví dụ trong công việc
Event Sự kiện khởi động tự động hóa Pull request được cập nhật
Workflow Quy trình được khai báo trong YAML Kiểm tra ứng dụng
Job Nhóm công việc được phân cho runner Chạy test với Node 24
Step Một bước thực thi trong job Chạy npm test
Action Thành phần tái sử dụng ở step Cài Node hoặc checkout code
Runner Máy thực thi job Máy Ubuntu do GitHub cấp
Artifact Tệp kết quả cần chuyển hoặc giữ lại Gói build hoặc saved plan
Environment Điểm áp dụng quy tắc triển khai production có bước duyệt

Các step thông thường chạy tuần tự trong cùng job và nhìn thấy các tệp đã được tạo ở step trước. Tuy nhiên, mỗi step run mở một tiến trình shell mới. Lệnh export NAME=value hoặc cd trong một step không tự duy trì cho step sau. Dùng cấu hình working-directory, $GITHUB_ENV hoặc output khi cần truyền thông tin. [G1, G6]

Các job không mặc nhiên dùng chung ổ đĩa. Job A tạo dist/ không làm job B có dist/; bạn phải upload rồi download artifact, hoặc chủ động dùng một hệ thống lưu trữ khác. needs tạo quan hệ phụ thuộc, không chuyển tệp. Với runner tự quản lý, tệp cũ có thể còn lại trên máy, nhưng không được lấy điều đó làm giao kèo truyền dữ liệu.

Một cách tự kiểm tra thiết kế là tưởng tượng job apply chạy trên máy mới hoàn toàn. Nếu nó chỉ thành công nhờ provider đã cài ở job plan hoặc nhờ thư mục cũ của lần chạy trước, pipeline còn phụ thuộc ngầm. Hãy khai báo lại toolchain, checkout đúng commit, init provider và lấy đúng artifact cần thiết.

3 YAML và workflow đầu tiên

Workflow đặt trong .github/workflows/ với đuôi .yml hoặc .yaml. YAML dùng thụt lề để mô tả cấu trúc, vì vậy sai khoảng trắng có thể thay đổi ý nghĩa. Dùng space, không dùng tab. Khi viết nhiều dòng shell, dùng |. [G2]

name: Learn Actions
on:
  workflow_dispatch:
permissions:
  contents: read
jobs:
  inspect:
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - name: Show execution identity
        shell: bash
        run: |
          printf 'Repository: %s\n' "$GITHUB_REPOSITORY"
          printf 'Commit: %s\n' "$GITHUB_SHA"
          pwd

Tạo tệp, commit vào nhánh mặc định rồi mở tab Actions để chạy thủ công. name là tên hiển thị. on chọn sự kiện. jobs.inspect là mã định danh job, còn tên hiển thị có thể đặt riêng. runs-on chọn runner; uses gọi action; with truyền input cho action; run chạy lệnh shell. Runner không tự có code của repository, vì vậy cần checkout.

permissions: contents: read đặt quyền đọc nội dung repository cho token của workflow. Nó không cấp quyền AWS. persist-credentials: false giảm việc giữ token checkout cho các lệnh Git tiếp theo; các step vẫn có thể được cấp token riêng nếu bạn chủ động truyền. Khi sau này cần push commit hoặc tạo release, chỉ cấp quyền bổ sung ở job thực sự làm việc đó.

push vào main Build hoặc triển khai code đã merge Bảo vệ nhánh và review workflow
workflow_dispatch Chạy lại hoặc thao tác vận hành Người dùng có thể chọn nhánh khi chạy
schedule Kiểm tra định kỳ Không phải bộ hẹn giờ bảo đảm đúng phút

Đây là các vai trò thiết kế thông dụng; chi tiết điều kiện chạy, ref và quyền token phụ thuộc từng event. Trước khi thêm trigger mới, đọc tài liệu event thay vì chỉ sao chép YAML từ một pipeline khác. [G3]

Trong pull_request.branches, main là nhánh đích của pull request. Với PR từ feature/network vào main, bộ lọc này phù hợp dù tên nhánh nguồn không chứa main. Mặc định checkout trên sự kiện PR thường kiểm tra merge ref để phát hiện lỗi tích hợp với nhánh đích. Khi cần chính xác head commit của PR, dùng github.event.pull_request.head.sha và ghi rõ bạn đang bỏ việc thử merge trong lần kiểm tra đó.

paths giảm số lần chạy nhưng có thể tạo lỗ hổng phạm vi: thay đổi module dùng chung hoặc script CI không nằm trong bộ lọc khiến pipeline không chạy. Một rủi ro khác là required check bị treo Pending nếu workflow bị bỏ qua bởi bộ lọc. Với check bắt buộc trước merge, cách khởi đầu dễ quản lý là luôn khởi động workflow; sau này mới thêm job phát hiện thay đổi và một job tổng hợp có tên ổn định. [G2]

Manual dispatch không đồng nghĩa với “luôn chạy code từ main”. Workflow triển khai mẫu kiểm tra github.ref == 'refs/heads/main' và checkout github.sha. Ở phía AWS và environment cũng phải có giới hạn tương ứng. Không dùng một chuỗi branch do người dùng nhập để quyết định trực tiếp code nào được chạy bằng quyền production.

Nếu kiểm tra drift lúc 9 giờ 17 phút ở Việt Nam, cron UTC tương ứng là 17 2 * * 1-5. Hãy kiểm tra quy ước timezone đang dùng khi thiết lập schedule. Lịch của Actions phù hợp kiểm tra định kỳ, không phù hợp nhiệm vụ có cam kết thời gian thực nghiêm ngặt.

5 Context expression biến và output

GitHub đánh giá biểu thức ${{ ... }} trong cấu hình; Bash đánh giá $NAME khi lệnh chạy trên runner. Hai thời điểm này khác nhau. Chẳng hạn if: github.ref == 'refs/heads/main' quyết định có chạy job hay không trước khi shell của job tồn tại. [G4, G5]

Cách truy cập Dữ liệu Cách dùng phù hợp
github.sha Commit gắn với event Truy vết code
github.ref Ref đầy đủ Giới hạn nhánh
vars.AWS_REGION Cấu hình không bí mật Region hoặc tên bucket state
secrets.API_TOKEN Giá trị bí mật đã cấu hình Xác thực dịch vụ khi chưa dùng OIDC
env.TF_VERSION Biến của workflow hoặc job Chọn phiên bản tool
steps.plan.outputs.exitcode Output từ một step có id Quyết định có thay đổi hay không
needs.plan.outputs.artifact_id Output job phụ thuộc Lấy đúng artifact plan

Tên role ARN hay account ID thường là cấu hình, không phải credentials. Có thể đặt chúng trong repository variables. Dữ liệu như mật khẩu database hoặc API token là secret. Tuy nhiên, mức bảo mật cuối cùng phụ thuộc cả nơi sử dụng: một secret bị truyền vào lệnh in log vẫn có nguy cơ lộ, dù GitHub có cơ chế che một số giá trị.

Ví dụ truyền output giữa các step:

- name: Compute a label
  id: label
  run: echo 'value=release-candidate' >> "$GITHUB_OUTPUT"
- name: Use the label
  env:
    BUILD_LABEL: ${{ steps.label.outputs.value }}
  run: printf '%s\n' "$BUILD_LABEL"

id là khóa để tham chiếu output, không phải name. Muốn truyền sang job khác, khai báo jobs.<job>.outputs rồi đọc bằng needs. Output phù hợp với dữ liệu nhỏ như ID và cờ trạng thái. Dùng artifact cho file và hệ thống quản lý secret cho bí mật. Không dựa vào output để vận chuyển secret giữa job. [G6]

Đầu vào từ PR có thể chứa ký tự shell. Không viết run: echo "${{ github.event.pull_request.title }}". Hãy đưa tiêu đề vào biến env, rồi dùng printf '%s\n' "$PR_TITLE". Cách này tránh biến nội dung PR thành một phần cú pháp shell; nó không khiến nội dung đó trở nên đáng tin để dùng làm lệnh, đường dẫn hoặc đối số nhạy cảm. [G7]

6 Thiết kế đồ thị job và xử lý lỗi

Trong pipeline lớn, chia job theo trách nhiệm và quyền. Test không cần khóa cloud; plan không cần quyền sửa toàn bộ hạ tầng; apply không cần quyền tạo comment lên PR. Tách job giúp nhìn rõ ranh giới này và cho phép chạy song song những kiểm tra độc lập.

jobs:
  lint:
    # Khai báo runs-on và steps của job lint
  test:
    # Khai báo runs-on và steps của job test
  package:
    needs: [lint, test]
    # Chỉ đóng gói sau khi các kiểm tra thành công

Đoạn trên chỉ minh họa đồ thị, chưa phải workflow chạy được. Khi dựng thật, mỗi job cần cấu hình đầy đủ. Mặc định nếu job phụ thuộc thất bại hoặc bị skip, job phía sau có thể bị skip theo. Một job tổng hợp dùng always() cần kiểm tra kết quả của tất cả job bắt buộc, không chỉ chạy một lệnh echo rồi báo xanh. [G2, G5]

continue-on-error: true hữu ích cho một kiểm tra thử nghiệm chưa bắt buộc, nhưng dễ che lỗi. Với Terraform plan, cách đúng là xử lý rõ mã thoát 0, 1, 2; không biến mọi lỗi thành thành công. Dùng if: failure() cho thu thập chẩn đoán, if: always() cho việc thực sự cần chạy sau mọi kết quả. Dọn tài nguyên vẫn có thể không hoàn tất nếu runner bị mất hoặc bị hủy cưỡng bức; cần cơ chế dọn độc lập cho tài nguyên tạm.

timeout-minutes giúp pipeline không treo vô hạn. Đặt timeout theo trách nhiệm: kiểm tra cú pháp vài phút; apply có thể cần lâu hơn vì API cloud bất đồng bộ. Timeout không hoàn tác thay đổi đã thực hiện, và hủy job apply cũng không bảo đảm hạ tầng trở về trạng thái ban đầu.

Matrix dùng cùng một logic với nhiều giá trị, ví dụ Node 22 và 24. fail-fast: false giúp bạn nhận đủ kết quả khi một phiên bản lỗi. max-parallel giới hạn số job cùng lúc. Với Terraform, chỉ chạy matrix song song cho các root module có state độc lập và đã xác định thứ tự phụ thuộc.

7 CI ứng dụng thực tế

Bộ lab có ứng dụng Node rất nhỏ tính tổng giá tiền theo đơn vị cent. Nó dùng số nguyên để tránh vấn đề số thập phân và có test cho dữ liệu sai, số lượng bằng không và tràn phạm vi số nguyên an toàn. Ví dụ này nhỏ để bạn tập trung vào pipeline; lint chỉ là kiểm tra cú pháp bằng Node, chưa thay thế một bộ ESLint hay kiểm tra chất lượng đầy đủ.

Workflow app-ci.yml thực hiện checkout, cài đúng Node theo matrix, cài dependency bằng npm ci, kiểm tra cú pháp, chạy test, build và upload kết quả. package-lock.json nằm trong Git. npm ci giúp môi trường CI dùng dependency theo lockfile và báo lỗi nếu lockfile không khớp manifest. Việc cache thư mục tải package không thay thế bước cài dependency.

Hai bản matrix tạo artifact khác tên, có phiên bản Node và commit SHA. Điều này tránh ghi đè hoặc nhầm kết quả. Với ứng dụng triển khai thật, hãy chọn một cấu hình build được hỗ trợ làm artifact phát hành, kiểm thử chính artifact đó và promote nó qua staging rồi production. Không build lại cùng một phiên bản ở mỗi môi trường rồi giả định kết quả giống nhau.

Thực hiện bài kiểm tra âm tính: sửa test để kỳ vọng 596 thay vì 597, mở PR và quan sát check đỏ. Nếu required checks được cấu hình đúng, PR không được merge. Sau khi sửa lại, checks xanh và merge được. Một workflow luôn xanh nhưng chưa từng chặn lỗi có thể đang không kiểm tra điều bạn nghĩ.

Khi mở rộng CI, thêm integration test với database tạm, scan dependency hoặc container, rồi chỉ publish image sau khi các kiểm tra bắt buộc thành công. Quyền packages: write chỉ đặt ở job publish. Image nên được truy vết bằng digest và commit; tag như latest chỉ là tên di động, không đủ làm bằng chứng phiên bản.

setup-node có thể quản lý cache npm dựa trên lockfile. Key nên phản ánh hệ điều hành, toolchain và dependency phù hợp. Cache có thể đến từ một phạm vi được phép chia sẻ; đừng xem nó là nguồn dữ liệu đáng tin cho triển khai. Đặc biệt không cache .terraform/ một cách mù quáng vì thư mục này có cấu hình backend và dữ liệu phụ thuộc vào lần init. [G8]

Artifact phục vụ kết quả cụ thể của lần chạy. Upload và download phải thống nhất ID hoặc tên có đủ ngữ cảnh. Gói plan có thể chứa dữ liệu nhạy cảm, nên repository riêng tư và quyền đọc artifact phải phù hợp. Thời gian lưu một ngày là lựa chọn của lab, không phải cơ chế làm sạch secret ngay lập tức hay thay thế kiểm soát truy cập. Nếu thông tin nhạy cảm bị lộ, xóa artifact chưa đủ; phải xử lý credentials liên quan. [G9]

Runner do GitHub cung cấp phù hợp để bắt đầu vì vòng đời và cài đặt đơn giản. Runner tự quản lý hữu ích khi cần mạng nội bộ, phần cứng đặc biệt hoặc kiểm soát môi trường. Đổi lại, bạn phải quản lý bản vá, cô lập, egress và dữ liệu tồn dư. Một runner dùng chung giữa PR chưa tin cậy và triển khai production tạo rủi ro lớn, kể cả nếu hai job không chạy cùng lúc.

Trong production, ưu tiên runner tạm thời cho mỗi job, phân nhóm runner theo mức tin cậy và chỉ cho repository cần thiết sử dụng. Nếu runner nằm trong AWS với instance profile mạnh, bất kỳ code nào chạy trên máy đều có thể tìm cách dùng quyền đó; việc không truyền secret từ GitHub không đồng nghĩa với không có quyền cloud.

Theo dõi thời gian chờ runner, thời gian từng job, tỷ lệ cache hit, số lần chạy trùng và dung lượng artifact. Tối ưu đoạn tốn thời gian thực tế trước. Matrix 4 hệ điều hành nhân 4 phiên bản có thể tạo 16 job; không cần ma trận đó nếu sản phẩm chỉ hỗ trợ một runtime và một nền tảng. Giới hạn và giá hiện hành cần xem trực tiếp trên tài khoản, không lấy một con số cố định làm giả định lâu dài.

9 Terraform dưới góc nhìn automation

Terraform đọc cấu hình khai báo, làm việc với provider và state để xác định thay đổi cần thực hiện. State là bản ánh xạ giữa địa chỉ trong cấu hình và tài nguyên thực tế, kèm nhiều thuộc tính. Nó không đơn giản là cache có thể xóa đi tạo lại. Mất hoặc dùng nhầm state có thể khiến Terraform định tạo trùng resource hoặc tác động sai hạ tầng.

Lệnh Điều cần hiểu khi đưa vào CI
fmt -check -recursive Kiểm tra định dạng và báo lỗi thay vì sửa trong CI
init -backend=false Cài module provider để kiểm tra mà không nối remote backend
validate Kiểm tra tính hợp lệ nội bộ sau init
plan Đọc cấu hình state và API cần thiết để tính thay đổi
plan -out=... Lưu bản kế hoạch máy đọc được để apply sau
apply <planfile> Thực thi bản plan đã lưu
plan -refresh-only Đánh giá cập nhật state theo tài nguyên thực tế

validate không chứng minh IAM đủ quyền, subnet tồn tại hay account có quota. Chỉ plan hoặc kiểm thử tích hợp phù hợp mới tiếp cận được các điều kiện runtime đó. init -backend=false vẫn có thể tải provider và module từ mạng, nên không có nghĩa là kiểm tra hoàn toàn offline hoặc không có rủi ro supply chain. [T1]

Với terraform plan -detailed-exitcode, mã 0 là thành công không có thay đổi, 2 là thành công có thay đổi, 1 là lỗi. Shell trong CI thường dừng khi gặp mã khác không. Mẫu workflow tạm tắt hành vi đó quanh đúng lệnh plan, lấy $? ngay sau lệnh, bật lại rồi chỉ chấp nhận 0 hoặc 2. Nếu dùng pipe qua tee, cần xử lý pipefail và mã của tiến trình Terraform, không lấy nhầm mã của tee. [T2]

terraform apply -auto-approve bỏ câu hỏi tương tác của Terraform, không phải một cơ chế duyệt thay đổi của tổ chức. Khi apply một saved plan, Terraform không yêu cầu phê duyệt tương tác như khi tự tạo plan mới. Do đó, gate phê duyệt phải đặt trước job apply và gắn với đúng saved plan. Không thêm -auto-approve theo thói quen để rồi tưởng nó giải quyết vấn đề CI. [T3]

Về kiểm thử, có thể dùng terraform test, mock provider phù hợp hoặc kiểm thử tích hợp trên account sandbox. Một test có thao tác apply có thể tạo tài nguyên thật và phát sinh chi phí; cần chính sách dọn tài nguyên, quota và timeout riêng. Test không thay thế việc review kế hoạch phá hủy hoặc thay thế resource. [T4]

10 Tổ chức repository và remote state

Lab dùng một root module ở infra/envs/prod/. Chữ prod mô phỏng quy trình production nhưng tài nguyên phải chạy trong account sandbox. Khi mở rộng, tạo root riêng cho staging và production, đồng thời tách account, role và state theo môi trường. Module dùng chung nằm ở thư mục riêng và được các root gọi lại.

Đường dẫn Trách nhiệm
.github/workflows/app-ci.yml CI ứng dụng
.github/workflows/terraform-check.yml Kiểm tra Terraform không dùng cloud credentials
.github/workflows/terraform-deploy.yml Tạo plan duyệt và apply
ci/plan_metadata.py Gắn plan với commit và lần chạy

infra/envs/prod/main.tf Bucket lab và cấu hình bảo vệ
app/ Ứng dụng nhỏ phục vụ CI

Cấu hình backend được truyền lúc init, không chứa access key. State key của lab là prod-lab/s3/terraform.tfstate. Cặp bucket và key chính là một phần danh tính hạ tầng; đổi sai một ký tự có thể khiến Terraform nhìn thấy một state rỗng. Trước lần chạy đầu, kiểm tra account, region, tên bucket và key bằng quy trình có người đối chiếu.

Backend S3 hiện hỗ trợ khóa bằng use_lockfile = true; khóa dùng DynamoDB đã được đánh dấu deprecated trong tài liệu chính thức. Với hệ thống đang dùng DynamoDB, cần kế hoạch tương thích phiên bản và di chuyển có kiểm tra, không xóa bảng khóa tùy tiện. Backend bucket phải tồn tại trước khi root module này init. [T5]

Bucket state nên bật versioning, mã hóa, chặn public access và có kiểm soát quyền đọc ghi. Nếu dùng KMS riêng, cấp thêm quyền KMS theo key và chính sách tương ứng. Quyền đọc state phải được xem như quyền tiếp cận dữ liệu nhạy cảm. sensitive = true chủ yếu che hiển thị thông thường; không tự loại giá trị khỏi state hoặc saved plan. Một số cơ chế ephemeral và write-only có thể tránh lưu dữ liệu trong các vị trí được hỗ trợ, nhưng cần xét từng provider và phiên bản. [T6]

Commit .terraform.lock.hcl để giữ lựa chọn provider và checksum. Constraint ~> 6.0 không khóa một patch cụ thể; lockfile mới làm các lần init sau chọn lại provider đã chốt. Lockfile không khóa phiên bản Terraform CLI hoặc mọi remote module. Với module, dùng version hay ref bất biến tương ứng. CI dùng -lockfile=readonly để yêu cầu việc nâng provider phải là thay đổi được review. [T7]

Concurrency của Actions và backend lock giải quyết hai tầng khác nhau. Concurrency giảm việc chạy chồng trong repository; backend lock bảo vệ state khi các client cùng truy cập backend đó, kể cả máy local hoặc hệ thống CI khác. Bạn cần cả hai. Không tắt khóa bằng -lock=false chỉ để pipeline xanh.

11 OIDC và phân quyền AWS

Thay vì lưu AWS access key dài hạn trong GitHub Secrets, OIDC cho phép job trình bày danh tính được GitHub ký để AWS STS cấp phiên làm việc tạm thời. Bạn cấu hình một IAM OIDC provider cho https://token.actions.githubusercontent.com, audience sts.amazonaws.com, rồi tạo IAM role chỉ tin các claim phù hợp. Job cần id-token: write để yêu cầu token OIDC. [G10]

Hãy hình dung ba lớp kiểm tra độc lập. GitHub cho phép job yêu cầu token; trust policy AWS quyết định token đó có được assume role không; permission policy của role quyết định phiên làm việc được gọi API nào. Một token có danh tính đúng vẫn không được làm điều nằm ngoài IAM policy. Ngược lại, permission policy chặt không sửa được trust policy cho phép sai repository assume role.

Lab có hai role. Plan role chỉ đọc cấu hình bucket lab và state, đồng thời được tạo xóa object khóa của state. Apply role được ghi state và quản lý bucket lab. Quyền ghi object khóa là ngoại lệ có chủ đích của plan role: “không sửa hạ tầng nghiệp vụ” không có nghĩa là tuyệt đối không có API ghi nào.

{
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub":
      "repo:YOUR_ORG/YOUR_REPO:ref:refs/heads/main"
  }
}

Đây là phần condition cho plan role của lab. Với apply job có environment: production, subject theo cấu hình mặc định đổi thành repo:YOUR_ORG/YOUR_REPO:environment:production, thay vì chuỗi ref của nhánh. Vì vậy phải dùng trust policy tương ứng và giới hạn nhánh triển khai trong GitHub environment. Không ghép cả hai giá trị subject thành điều kiện đồng thời rồi kỳ vọng token thỏa mãn. Nếu tổ chức tùy biến subject OIDC, cần đối chiếu claim thực tế. [G10]

Bộ mã có đầy đủ plan-trust.json, apply-trust.json và hai permission policy trong iam/. Thay mọi placeholder trước khi dùng. Policy apply cho phép s3:* nhưng chỉ trên ARN bucket lab và object của nó; đây là cách giới hạn phạm vi tài nguyên để làm bài học dễ vận hành, chưa phải tập API tối thiểu cho một hệ thống production. Khi triển khai thật, thu hẹp action theo provider, CloudTrail và kiểm thử; không thay bằng AdministratorAccess để bỏ qua lỗi.

Hai role cần quyền khác nhau trên bucket state. Plan: GetObject trên state; apply: thêm PutObject trên state. Cả hai cần GetObject, PutObject, DeleteObject trên tệp .tflock. Policy mẫu cho phép ListBucket trên bucket state để việc init và khám phá workspace không bị chặn; quyền đọc ghi object vẫn giới hạn đúng key. Có thể thu hẹp quyền liệt kê sau khi xác minh các prefix mà backend thực sự gọi. Nếu dùng KMS, bucket policy hay SCP, những lớp đó còn có thể từ chối request dù role policy có Allow.

12 Luồng Terraform được đề xuất

Luồng mẫu chọn sự đơn giản về mức tin cậy: PR chỉ kiểm tra không có credentials; chỉ code đã vào main mới được plan với quyền cloud. Sau khi plan có thay đổi, job apply chờ environment approval. Quyết định này phù hợp để học an toàn, đồng thời giải thích rõ sự đánh đổi: reviewer PR chưa nhìn thấy cloud plan tự động trước merge.

  1. Người phát triển sửa Terraform trên nhánh chức năng và mở PR.
  2. Terraform Check chạy format, init không backend và validate trên runner GitHub.
  3. Reviewer xem code, module, workflow và policy. Required checks phải đạt trước merge.
  4. Push lên main kích hoạt Terraform Deploy. Job plan assume plan role qua OIDC.
  5. Job plan nối đúng backend, validate lại và tạo saved plan cùng bản text để review.
  6. Nếu không có thay đổi, workflow kết thúc mà không mở job apply.
  7. Nếu có thay đổi, người duyệt tải đúng artifact của run, xem plan và xác nhận environment.
  8. Job apply xác minh commit, metadata, checksum và thời hạn plan; assume apply role rồi apply saved plan.
  9. Người vận hành kiểm tra trạng thái hạ tầng, state và bằng chứng trong workflow run.

Tại sao phải tạo plan mới sau merge? Plan từ PR có thể dựa trên merge ref khác, state khác hoặc code đã thay đổi. Workflow sau merge tính lại kế hoạch từ commit thực sự nằm trên nhánh triển khai. Người duyệt apply phải xem kế hoạch mới này; review code trước merge và review plan trước apply là hai bước phục vụ hai loại bằng chứng khác nhau.

Trong doanh nghiệp muốn xem plan trước merge, có thể thêm một luồng plan đặc quyền cho commit đã được tin cậy, hoặc dùng HCP Terraform hay hệ thống điều phối chuyên dụng. Việc kiểm tra “PR đến từ cùng repository” không đủ biến toàn bộ code thành tin cậy. Chỉ cấp role cloud cho PR sau khi có mô hình phê duyệt, cô lập và kiểm soát egress phù hợp; plan có thể thực thi provider và đọc nhiều dữ liệu nhạy cảm.

13 Thiết lập bài lab từ đầu

13.1 Chuẩn bị môi trường

Dùng repository riêng tư trên GitHub.com và AWS account sandbox. Bucket nghiệp vụ của lab không nên chứa dữ liệu thật. Bạn cần quyền tạo IAM role, OIDC provider và bucket state theo quy định của tổ chức; nếu không có, nhờ quản trị viên thiết lập phần bootstrap. Không cấp quyền AWS quản trị cho workflow để tự dựng chính trust boundary của nó.

Giải nén bộ ví dụ vào thư mục repository mới, bảo đảm .github/, infra/, ci/ và app/ nằm ngay dưới root. Một số chương trình giải nén không hiển thị thư mục bắt đầu bằng dấu chấm; cần kiểm tra rằng các tệp workflow đã có trong Git. Đổi team placeholder ở CODEOWNERS thành team thật, hoặc thay bằng tài khoản reviewer phù hợp.

Tạo bucket state riêng, ví dụ my-company-tfstate-sandbox-unique, bật Block Public Access, versioning và mã hóa. Bucket này không phải bucket lab mà Terraform sẽ quản lý. Không đưa bucket state vào cùng root module sẽ xóa khi dọn lab. Nếu tổ chức dùng S3 Object Lock hoặc KMS, phải kiểm tra khả năng xóa lockfile và quyền mã hóa trước.

13.2 Thiết lập danh tính và quyền

Tạo OIDC provider và hai role theo chương 11. Trong các JSON mẫu, thay account ID 123456789012, YOUR_ORG/YOUR_REPO, YOUR_STATE_BUCKET, YOUR_LAB_BUCKET. Chữ hoa chữ thường của tên repository và environment phải khớp cấu hình danh tính của bạn. Gắn permission policy vào đúng role, không gắn trust policy như một permission policy thông thường.

Trong repository, tạo các Actions variables sau. Lab dùng repository variables cho cả plan và apply để tránh job plan vô tình phụ thuộc environment production.

Variable Ví dụ hoặc ý nghĩa
AWS_ACCOUNT_ID Account sandbox có 12 chữ số
AWS_REGION ap-southeast-1
AWS_PLAN_ROLE_ARN ARN role tạo plan
AWS_APPLY_ROLE_ARN ARN role apply
TF_STATE_BUCKET Bucket state đã bootstrap
LAB_BUCKET_NAME Tên bucket lab duy nhất toàn cục

Workflow truyền LAB_BUCKET_NAME thành TF_VAR_bucket_name. Cùng một giá trị được dùng trong policy IAM cho bucket lab. Chọn tên thông thường gồm chữ thường, số và dấu gạch nối; validation minh họa trong Terraform không bao quát mọi quy tắc và tên dành riêng của S3.

13.3 Cấu hình environment và bảo vệ nhánh

Tạo environment tên chính xác production trước khi chạy deploy. Chỉ cho phép nhánh main triển khai, bật required reviewers và ngăn tự duyệt nếu tính năng được hỗ trợ. Quy định việc bypass protection và quyền admin cần rõ ràng. Chỉ viết environment: production trong YAML không tự tạo ra chính sách duyệt đủ mạnh. [G11]

Khả năng dùng environment protection và required reviewers phụ thuộc gói GitHub, kiểu repository và chính sách tổ chức. Nếu repo của bạn không hỗ trợ bước duyệt cần thiết, dừng phần apply tự động và dùng công cụ triển khai có approval phù hợp. Một nút manual dispatch tự nó không chứng minh người dùng đã duyệt đúng saved plan. Không chạy apply với production role khi gate chưa được thiết lập.

Đặt ruleset hoặc branch protection cho main: bắt buộc PR, bắt buộc check của App CI và Terraform Check, hạn chế push trực tiếp và yêu cầu owner review cho workflow cùng mã hạ tầng. Chọn tên check từ những lần chạy thực tế để tránh nhập sai. Nếu dùng merge queue, giữ trigger merge_group trong các workflow kiểm tra. Gói terraform-deploy.yml dùng path filter và không nên đặt chính nó làm required check của PR.

13.4 Tạo provider lockfile và chạy kiểm tra local

Cài Terraform CLI đúng phiên bản 1.14.6 trên máy của bạn hoặc máy chuẩn bị được quản lý. Từ root repository chạy:

terraform fmt -recursive infra
terraform -chdir=infra/envs/prod init -backend=false
terraform -chdir=infra/envs/prod providers lock \
  -platform=linux_amd64
terraform -chdir=infra/envs/prod validate
git add infra/envs/prod/.terraform.lock.hcl

Nếu phát triển trên nền tảng khác, thêm platform tương ứng khi tạo lockfile. Review thay đổi provider và checksum, rồi commit lockfile. Đây là bước bắt buộc trước khi workflow có -lockfile=readonly chạy. Bộ ví dụ không tự điền checksum vì checksum phải lấy từ provider thật qua quá trình init hoặc providers lock. Không commit .terraform/.

Trong app/, chạy npm ci, npm run lint, npm test và npm run build với Node 24. Commit code lên nhánh chức năng. Mở PR và quan sát cả hai check. Pipeline deploy chỉ chạy sau merge khi có thay đổi thuộc phạm vi lọc, hoặc khi bạn dispatch thủ công từ main.

13.5 Thực hiện một lần thay đổi hoàn chỉnh

Ở lần đầu, plan thường cho thấy tạo bucket cùng cấu hình chặn public access và mã hóa. Tải artifact tfplan-<run_id>-<run_attempt> từ đúng run. Giải nén tệp plan-bundle.tgz, đọc plan.txt và đối chiếu metadata. Không chạy bất kỳ script nào lấy từ artifact PR chưa tin cậy. Với lab, artifact này chỉ do workflow trên main tạo ra.

Người duyệt kiểm tra tên bucket, account sandbox, region, số lượng create/update/delete/replace và mọi thay đổi ngoài phạm vi dự kiến. Sau khi approve environment, apply tiếp tục. Kiểm tra bucket trong AWS, trạng thái workflow và object state trong bucket backend. Chạy lại workflow: nếu cấu hình và hạ tầng không thay đổi, plan trả 0, apply bị skip. Đây là một bài kiểm tra tính hội tụ hữu ích.

Để làm một thay đổi tiếp theo, sửa tag có ý nghĩa hoặc thêm một cấu hình được review. Quan sát khác biệt giữa update tại chỗ và replacement. Không dùng dữ liệu production để thử thao tác phá hủy. Việc tạo bucket thường nhỏ nhưng các API, lưu trữ và tính năng bổ sung vẫn có thể phát sinh chi phí theo tài khoản.

14 Đọc workflow kiểm tra và triển khai

14.1 Terraform Check

Workflow này chạy trên PR, push main và merge group. Nó chỉ có contents: read, không yêu cầu OIDC và không đọc secret cloud. Format kiểm tra toàn bộ thư mục infra; init và validate chạy ở root module của lab. Nếu bạn thêm root module mới mà không mở rộng workflow, nó chỉ được format chứ chưa được validate. Đây là trách nhiệm cần nhớ khi nhân bản ví dụ.

init -backend=false giữ bước kiểm tra không nối bucket state. -lockfile=readonly giúp phát hiện provider chưa được khóa đúng hoặc yêu cầu dependency mới. validate vẫn chạy với các variable chưa có giá trị thực tế nếu cấu hình cho phép; nó không thay thế plan với giá trị môi trường thật.

14.2 Job plan

Job chỉ chạy từ main, checkout commit cụ thể, cài Terraform cố định và assume plan role. allowed-account-ids tạo thêm kiểm tra account trong action cấu hình credentials, nhưng không thay thế IAM. Sau đó init truyền backend bucket, key, region, encryption và native locking. Các giá trị này không phải mật khẩu; AWS credentials đi qua biến môi trường của phiên STS. [G20]

Plan lưu binary tại bundle/tfplan và chuyển cả stdout lẫn stderr vào bundle/plan.txt. Cách này giảm việc vô tình đẩy toàn bộ plan vào log chung. Với repository riêng tư của lab, bản text nằm trong artifact để người có quyền review đọc. Khi plan lỗi, artifact chẩn đoán chứa bản text được upload riêng; cần bảo vệ quyền đọc artifact tương tự state.

Nếu plan trả 2, workflow đóng gói plan, bản text, provider lockfile, metadata và checksum. Nó xuất ID artifact thành output job. Nếu plan trả 0, không tạo artifact triển khai và không chạy apply. Nếu trả 1 hoặc mã bất thường, job phải đỏ. Không cho apply chạy chỉ vì output không rỗng.

14.3 Job apply

Job có needs: plan, chỉ chạy khi exit code là 2 và chờ environment protection. Runner mới checkout cùng SHA, cài cùng Terraform, download artifact bằng đúng ID do job plan trả về. Trước khi lấy quyền cloud, nó đối chiếu head hiện tại của main, kiểm checksum, so lockfile và chạy xác minh metadata.

Sau kiểm tra, job assume apply role, init lại cùng backend rồi chạy terraform apply ... bundle/tfplan. Nó không chạy terraform plan lần nữa và không truyền bộ biến khác cho apply. Dữ liệu dùng để quyết định thay đổi đã nằm trong saved plan; nếu cần đổi input, phải tạo và duyệt plan mới.

Mẫu không tự đưa nội dung plan vào PR comment hoặc summary vì plan có thể mang dữ liệu nhạy cảm. Summary chỉ ghi SHA, mã thoát và đường dẫn artifact. Mẫu cũng chưa có policy engine tự chặn delete, đánh giá chi phí hoặc ticket change management; thêm các bước này trước gate apply nếu môi trường yêu cầu.

15 Bảo đảm apply đúng plan đã duyệt

Một quy trình dễ sai là plan ở job A, người duyệt, rồi job B chạy terraform apply không có planfile. Lần apply đó tự tính kế hoạch mới. Người duyệt đã nhìn một kế hoạch, nhưng job thực hiện một kế hoạch có thể khác. Saved plan và artifact theo ID giúp gắn hai giai đoạn lại với nhau. [T2, T3, G21]

Lab lưu repository, sha, run_id, run_attempt, terraform_version, state_key và thời điểm tạo. Script từ chối khi một trường không khớp hoặc plan quá 4 giờ. Đây là chính sách minh họa; đội của bạn cần chọn thời hạn phù hợp với tốc độ thay đổi và thời gian review. Artifact giữ một ngày không có nghĩa plan có thể dùng suốt một ngày.

Vì run_attempt được kiểm tra, thao tác “Re-run failed jobs” chỉ chạy apply ở attempt mới có thể bị từ chối. Chủ động dùng “Re-run all jobs” để tạo plan mới, rồi review và approve lại. Không sửa script để bỏ qua mismatch chỉ vì muốn dùng lại một plan thuận tiện. Nếu state đã đổi do một lần apply khác, saved plan cũng có thể bị Terraform từ chối là stale.

Checksum giúp phát hiện tệp hỏng hoặc gói không nhất quán; một checksum nằm cùng artifact không chứng minh tác giả đáng tin. Người kiểm soát cả workflow tạo plan có thể tạo cả checksum giả. Ranh giới tin cậy nằm ở việc bảo vệ nhánh, review workflow, action đã pin và quyền ghi artifact. Khi cần xác minh provenance mạnh hơn, thiết kế thêm attestation hoặc chữ ký và bộ xác minh độc lập phù hợp.

Kiểm tra head main trước apply giúp từ chối plan thuộc commit cũ khi đã có commit mới. Vẫn tồn tại khoảng thời gian sau kiểm tra mà nhánh có thể tiếp tục thay đổi; YAML không phải giao dịch khóa nhánh Git. Với yêu cầu nghiêm ngặt, dùng hàng đợi triển khai, freeze thay đổi theo change window hoặc hệ thống điều phối đảm bảo thứ tự mong muốn. Không tuyên bố rằng một lệnh so SHA giải quyết mọi race condition.

Backend lock được giữ khi Terraform làm thao tác cần khóa, không được giữ suốt thời gian người duyệt đang đọc artifact. Một client khác vẫn có thể apply giữa plan và apply. Ngoài ra, thay đổi trực tiếp ngoài Terraform có thể chưa làm state serial đổi; saved plan không bảo đảm phát hiện mọi drift phát sinh sau lúc lập kế hoạch. Giữ thời gian chờ ngắn và tái plan khi có nghi ngờ về trạng thái thực tế.

Concurrency trong lab đặt ở cấp workflow với group cố định cho state này và cancel-in-progress: false. Nó tránh chủ động hủy một lần apply đang chạy khi có push mới. Cơ chế xếp pending và thứ tự không nên bị hiểu thành hàng đợi FIFO bền vững; tùy cấu hình concurrency hiện hành, pending run có thể bị thay thế. Nếu mọi commit đều phải được deploy theo thứ tự, cần một cơ chế hàng đợi đáp ứng chính yêu cầu đó. [G12]

16 Bảo mật workflow trong môi trường thật

16.1 Code từ pull request chưa có mức tin cậy production

PR có thể thay script, module, provider, Dockerfile, package lifecycle script và cả workflow. Không chỉ shell inline mới thực thi code. npm ci, test hoặc plan đều có thể gọi code từ thay đổi. Vì vậy, lab không cấp quyền cloud cho PR và dùng GitHub hosted runner thay vì runner có quyền truy cập mạng production.

Đặc biệt thận trọng với pull_request_target và workflow_run. Chúng có thể tạo ngữ cảnh đặc quyền khác với pull_request. Không tải artifact hay checkout code từ PR chưa tin cậy rồi chạy nó trong job có secret hoặc quyền ghi. Các rào chắn mới của action checkout giúp giảm một số sai sót, nhưng không thay thế mô hình phân quyền của bạn. [G7, G16]

16.2 Quyền của token và action bên ngoài

Đặt quyền mặc định tối thiểu và mở ở từng job. Đọc code chỉ cần contents: read; xin OIDC cần id-token: write; comment PR cần quyền riêng. Không dùng một PAT quản trị cho cả repository khi GITHUB_TOKEN hoặc GitHub App với quyền hẹp có thể đáp ứng. Quyền mặc định ở tổ chức, sự kiện fork và chính sách quản trị có thể làm quyền thực tế khác điều bạn kỳ vọng.

Action bên ngoài chạy code trong ngữ cảnh job. Kiểm tra chủ sở hữu, release, commit và hành vi trước khi dùng. Pin commit SHA đầy đủ, ghi comment phiên bản để dễ đọc, và dùng Dependabot hoặc cơ chế tương tự mở PR cập nhật. Tag major tiện cho bài học nhưng có thể trỏ sang commit mới theo thời gian. Dùng action chính chủ cũng vẫn cần theo dõi cập nhật và quyền được cấp. [G7]

16.3 Secret state plan và log

Không commit access key, state, plan binary hoặc tfvars chứa secret. Có .gitignore không đủ nếu tệp đã được theo dõi trong Git từ trước. Khi lộ secret, thu hồi hoặc rotate trước, sau đó xử lý lịch sử và các bản sao theo quy trình tổ chức. Đừng chỉ xóa dòng secret ở commit mới rồi coi sự cố đã xong.

Không bật set -x trong step có secret. Không dump toàn bộ context GitHub hay tất cả biến môi trường để debug. terraform show -json có thể trả dữ liệu nhạy cảm dạng rõ; chỉ dùng cho policy engine trong phạm vi được bảo vệ và không tự đăng JSON lên PR công khai. Việc đặt sensitive không làm plan binary trở thành artifact an toàn để công bố. [T6]

16.4 Approval phải bảo vệ cả đường đi đến quyền cloud

Environment reviewer, branch rule, CODEOWNERS và OIDC trust policy cần thống nhất. Nếu ai đó được sửa workflow rồi merge không qua review, họ có thể thêm một job khác mang environment production và dùng apply role cho lệnh khác. AWS chỉ thấy danh tính được trust, không tự hiểu “lệnh Terraform được phép” trong YAML.

Khi cần bảo đảm chỉ workflow triển khai chuẩn được assume role, xem xét ràng buộc danh tính workflow dùng chung bằng các khả năng claim và subject customization mà tổ chức cùng cloud hỗ trợ, rồi kiểm chứng chính xác. Đừng giả định AWS tự hỗ trợ mọi custom claim của GitHub trong trust policy. Tách workflow chuẩn về repository do platform team quản lý cũng chỉ hữu ích nếu quyền gọi, ref và đường nâng quyền được kiểm soát.

17 Tái sử dụng và mở rộng nhiều môi trường

17.1 Reusable workflow và composite action

Reusable workflow phù hợp khi bạn muốn chia sẻ cả một quy trình gồm job, runner và quyền. Composite action gom một chuỗi step để chạy trong job của bên gọi. Chọn theo ranh giới cần chia sẻ, không chọn chỉ vì thấy cú pháp ngắn hơn. Workflow dùng chung nên có input được định kiểu, ít quyền và giao diện ổn định. [G13]

# Minh họa một job gọi workflow đã được platform team quản lý
jobs:
  validate:
    permissions:
      contents: read
    uses: YOUR_ORG/platform/.github/workflows/tf-check.yml@REPLACE_WITH_FULL_SHA
    with:
      root: infra/envs/prod
      terraform_version: '1.14.6'

Đây là đoạn minh họa kiến trúc, không phải tệp gọi được ngay: repository đích phải tồn tại và workflow phải khai báo on: workflow_call với các input tương ứng. Với workflow ở repository khác, quyền truy cập và chính sách Actions còn phải cho phép sử dụng. Không dùng secrets: inherit một cách mặc định nếu workflow chỉ cần một secret cụ thể.

Kiểm tra input root bằng allowlist nếu bên gọi có thể chọn đường dẫn; không ghép thẳng input vào shell. Workflow dùng chung cũng cần test và chiến lược nâng phiên bản. Pin vào SHA giúp repository sử dụng không đổi hành vi đột ngột khi platform team push lên main.

17.2 Nhiều root module và nhiều môi trường

Với hai môi trường, thường nên tách infra/envs/staging và infra/envs/prod, mỗi nơi có state riêng và role riêng. Không chỉ đổi tên GitHub environment mà vẫn giữ cùng bucket/key state. Tách AWS account giúp giảm phạm vi ảnh hưởng; cần xét cả dịch vụ dùng chung và đường kết nối mạng giữa account.

Terraform workspace là cách tách state trong một backend, không tự tách credentials hoặc tạo boundary IAM mạnh. Nó có thể phù hợp với các bản sao cùng mô hình, nhưng không nên được xem là lời giải duy nhất cho phân tách staging và production. Chọn directory, account, backend và workspace dựa trên yêu cầu truy cập và vòng đời thay đổi.

Chạy song song stack độc lập như DNS sandbox và monitoring sandbox khi chúng không phụ thuộc nhau. Với network rồi database rồi application, cần thứ tự và giao diện output rõ ràng. Một matrix khổng lồ không diễn đạt được mọi quan hệ phụ thuộc. Tránh một state quá lớn, nhưng cũng tránh chia nhỏ đến mức mỗi thay đổi phải điều phối hàng chục state không có người chịu trách nhiệm.

17.3 Monorepo và kiểm tra chính sách

Trong monorepo, thay đổi module dùng chung phải kích hoạt mọi root module bị ảnh hưởng. Danh sách file thay đổi chưa đủ nếu không có bản đồ phụ thuộc. Có thể bắt đầu với validate tất cả root module, sau đó đo thời gian và chỉ tối ưu khi cần. Required check tổng hợp phải báo đúng lỗi và không xanh khi các kiểm tra quan trọng bị skip.

Policy có thể chặn resource public, region ngoài allowlist hoặc replacement database. Với policy đọc plan JSON, giữ dữ liệu trong môi trường bảo vệ và kiểm tra cả giá trị chưa biết tại thời điểm plan. Dòng “policy passed” chỉ chứng minh các quy tắc đã cài đạt; nó không chứng minh hạ tầng tuân thủ mọi tiêu chuẩn chưa được mã hóa.

18 Drift rollback và vận hành sự cố

18.1 Phát hiện và xử lý drift

Drift là khác biệt giữa hạ tầng thực tế và trạng thái mong muốn do thay đổi ngoài luồng hoặc hành vi dịch vụ. Một lịch plan định kỳ với quyền plan có thể phát hiện chênh lệch. Trả mã 2 nghĩa là cần phân loại; không mặc định tự apply, vì kế hoạch có thể bao gồm thay đổi cấu hình chưa triển khai hoặc hành động khôi phục một can thiệp khẩn cấp có chủ đích.

Đội vận hành cần quyết định: đưa hạ tầng trở lại cấu hình Git, cập nhật Git để chấp nhận thay đổi ngoài luồng, hay thực hiện import/migration có review. Lưu ticket và người chịu trách nhiệm. Nếu phát hiện drift trên IAM, network hoặc database, xem lại mức ưu tiên thay vì xử lý như một cảnh báo định dạng code.

18.2 Vì sao rollback Terraform không giống rollback ứng dụng

Rollback ứng dụng thường có thể trỏ về image digest cũ. Với Terraform, revert commit rồi apply vẫn tạo một kế hoạch mới trên hạ tầng hiện tại. Nó có thể thay thế tài nguyên, không khôi phục dữ liệu đã mất và không bảo đảm trở lại trạng thái cũ. Đọc kỹ plan của thao tác revert như một thay đổi mới.

Versioning của bucket state hỗ trợ điều tra và khôi phục state trong sự cố thích hợp. Nó không phải backup dữ liệu database, và restore state cũ có thể làm ánh xạ resource lệch với thực tế. Chỉ phục hồi state theo quy trình được kiểm soát, đã sao lưu state hiện tại và đối chiếu tài nguyên cloud. Không sửa serial hoặc ghi đè state để ép một saved plan cũ được apply.

18.3 Khi apply thất bại giữa chừng

  1. Chặn các lần triển khai tiếp theo cho cùng state và giữ lại log cùng run ID.
  2. Xác định API nào đã thành công, API nào lỗi và có tác vụ cloud nào còn chạy.
  3. Kiểm tra backend lock, phiên STS, state hiện tại và tài nguyên liên quan.
  4. Chạy plan mới từ code đã được xác nhận để xem Terraform nhận diện phần hoàn tất thế nào.
  5. Review và duyệt kế hoạch sửa chữa; chỉ import, move hoặc chỉnh state khi đã xác minh ánh xạ.
  6. Ghi nguyên nhân, biện pháp phòng ngừa và xác nhận mở lại triển khai.

Không bấm rerun liên tục khi chưa hiểu trạng thái. Một resource có thể đã tạo ở cloud nhưng chưa được ghi nhận như mong muốn nếu có lỗi ghi state hoặc runner mất kết nối. Cách khắc phục phụ thuộc resource và sự cố cụ thể, không phải luôn xóa thủ công rồi tạo lại.

18.4 Khóa state và quyền khẩn cấp

Khi gặp lock, tìm owner, operation, thời điểm và các pipeline liên quan. Nếu còn apply hoạt động, chờ hoặc xử lý nó có kiểm soát. force-unlock chỉ dùng khi xác nhận khóa mồ côi và không còn tiến trình giữ khóa. Cần đúng backend, đúng state và đúng lock ID; không xóa mọi .tflock cho nhanh. [T8]

Quyền khẩn cấp nên tách khỏi role workflow thường ngày, có thời hạn và được ghi audit. Sau khi dùng, chạy lại kiểm tra drift, đồng bộ Git và đóng sự cố. Nếu cùng một người vừa được bỏ branch protection vừa tự duyệt production không có dấu vết bổ sung, gate trong YAML sẽ không mang lại kiểm soát như kỳ vọng.

18.5 Dọn tài nguyên bài lab

Sau khi học, lập kế hoạch destroy trong account sandbox bằng quy trình riêng có review: init đúng backend, terraform plan -destroy -out=destroy.tfplan, xem kế hoạch rồi terraform apply destroy.tfplan. Bộ workflow không tự động destroy. Bucket lab đặt force_destroy = false, nên bucket có dữ liệu phải được xử lý có chủ đích trước khi xóa.

Chỉ dọn bucket state, IAM role và OIDC provider sau khi xác nhận không có lab hoặc workflow khác dùng chung. Có thể giữ bucket state để lưu audit theo thời hạn tổ chức. Không để một lệnh destroy theo lịch chạy bằng production role mà không có danh sách phạm vi và cơ chế duyệt phù hợp.

name: Terraform Deploy
on:
  push:
    branches: [main]
    paths:
      - 'infra/**'
      - 'ci/**'
      - '.github/workflows/terraform-*.yml'
  workflow_dispatch:
permissions:
  contents: read
concurrency:
  group: terraform-prod-lab
  cancel-in-progress: false
env:
  TF_IN_AUTOMATION: 'true'
  TF_INPUT: 'false'
  TF_VERSION: '1.14.6'
  AWS_REGION: ${{ vars.AWS_REGION }}
  TF_VAR_bucket_name: ${{ vars.LAB_BUCKET_NAME }}
  TF_VAR_aws_region: ${{ vars.AWS_REGION }}
defaults:
  run:
    shell: bash
    working-directory: infra/envs/prod
jobs:
  plan:
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    timeout-minutes: 20
    permissions:
      contents: read
      id-token: write
    outputs:
      exitcode: ${{ steps.plan.outputs.exitcode }}
      artifact_id: ${{ steps.upload.outputs.artifact-id }}
    steps:
      - uses: actions/checkout@v7
        with:
          ref: ${{ github.sha }}
          persist-credentials: false
      - uses: hashicorp/setup-terraform@v4
        with:
          terraform_version: ${{ env.TF_VERSION }}
          terraform_wrapper: false
      - run: terraform fmt -check -recursive ../../..
      - uses: aws-actions/configure-aws-credentials@v6.3.0
        with:
          role-to-assume: ${{ vars.AWS_PLAN_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
          role-session-name: gha-plan-${{ github.run_id }}
          allowed-account-ids: ${{ vars.AWS_ACCOUNT_ID }}
      - name: Initialize remote state
        env:
          STATE_BUCKET: ${{ vars.TF_STATE_BUCKET }}
        run: |
          terraform init -input=false -lockfile=readonly \
            -backend-config="bucket=$STATE_BUCKET" \
            -backend-config="key=prod-lab/s3/terraform.tfstate" \
            -backend-config="region=$AWS_REGION" \
            -backend-config="encrypt=true" \
            -backend-config="use_lockfile=true"
      - run: terraform validate -no-color
      - name: Generate saved plan
        id: plan
        run: |
          mkdir -p bundle
          set +e
          terraform plan -input=false -no-color -lock-timeout=5m \
            -detailed-exitcode -out=bundle/tfplan > bundle/plan.txt 2>&1
          rc=$?
          set -e
          echo "exitcode=$rc" >> "$GITHUB_OUTPUT"
          if [[ "$rc" != 0 && "$rc" != 2 ]]; then
            echo '::error::Terraform plan failed. Review the restricted diagnostics artifact.'
            exit 1
          fi
      - name: Save restricted plan diagnostics on failure
        if: failure() && steps.plan.outcome == 'failure'
        uses: actions/upload-artifact@v7
        with:
          name: tf-plan-error-${{ github.run_id }}-${{ github.run_attempt }}
          path: infra/envs/prod/bundle/plan.txt
          if-no-files-found: warn
          retention-days: 1
      - name: Package plan and review text
        if: steps.plan.outputs.exitcode == '2'
        run: |
          cp .terraform.lock.hcl bundle/
          python3 ../../../ci/plan_metadata.py create bundle
          (cd bundle && sha256sum tfplan plan.txt metadata.json \
            .terraform.lock.hcl > SHA256SUMS)
          tar -czf plan-bundle.tgz -C bundle .
      - uses: actions/upload-artifact@v7
        if: steps.plan.outputs.exitcode == '2'
        id: upload
        with:
          name: tfplan-${{ github.run_id }}-${{ github.run_attempt }}
          path: infra/envs/prod/plan-bundle.tgz
          if-no-files-found: error
          retention-days: 1
      - name: Write review instructions
        env:
          PLAN_EXIT: ${{ steps.plan.outputs.exitcode }}
          ARTIFACT_URL: ${{ steps.upload.outputs.artifact-url }}
        run: |
          {
            echo "Commit: $GITHUB_SHA"
            echo "Terraform plan exit code: $PLAN_EXIT"
            echo "Plan bundle: $ARTIFACT_URL"
            echo 'Review plan.txt in the restricted artifact before approval.'
            echo 'Approval is valid only for this commit and plan bundle.'
          } >> "$GITHUB_STEP_SUMMARY"
  apply:
    needs: plan
    if: >-
      github.ref == 'refs/heads/main' &&
      needs.plan.outputs.exitcode == '2'
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    environment: production
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v7
        with:
          ref: ${{ github.sha }}
          persist-credentials: false
      - uses: hashicorp/setup-terraform@v4
        with:
          terraform_version: ${{ env.TF_VERSION }}
          terraform_wrapper: false
      - uses: actions/download-artifact@v8
        with:
          artifact-ids: ${{ needs.plan.outputs.artifact_id }}
          path: infra/envs/prod/received
      - name: Verify commit and plan bundle before cloud login
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          latest=$(gh api "repos/$GITHUB_REPOSITORY/git/ref/heads/main" --jq .object.sha)
          test "$latest" = "$GITHUB_SHA"
          mkdir -p bundle
          tar -xzf received/plan-bundle.tgz -C bundle
          (cd bundle && sha256sum -c SHA256SUMS)
          cmp .terraform.lock.hcl bundle/.terraform.lock.hcl
          python3 ../../../ci/plan_metadata.py verify bundle
      - uses: aws-actions/configure-aws-credentials@v6.3.0
        with:
          role-to-assume: ${{ vars.AWS_APPLY_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
          role-session-name: gha-apply-${{ github.run_id }}
          allowed-account-ids: ${{ vars.AWS_ACCOUNT_ID }}
      - name: Initialize remote state
        env:
          STATE_BUCKET: ${{ vars.TF_STATE_BUCKET }}
        run: |
          terraform init -input=false -lockfile=readonly \
            -backend-config="bucket=$STATE_BUCKET" \
            -backend-config="key=prod-lab/s3/terraform.tfstate" \
            -backend-config="region=$AWS_REGION" \
            -backend-config="encrypt=true" \
            -backend-config="use_lockfile=true"
      - name: Apply the reviewed saved plan
        run: terraform apply -input=false -no-color -lock-timeout=5m bundle/tfplan

import time

mode, directory = sys.argv[1:]
path = Path(directory) / 'metadata.json'
expected = {
    'repository': os.environ['GITHUB_REPOSITORY'],
    'sha': os.environ['GITHUB_SHA'],
    'run_id': os.environ['GITHUB_RUN_ID'],
    'run_attempt': os.environ['GITHUB_RUN_ATTEMPT'],
    'terraform_version': os.environ['TF_VERSION'],
    'state_key': 'prod-lab/s3/terraform.tfstate',
}
if mode == 'create':
    path.write_text(json.dumps({**expected, 'created_at': time.time()}, indent=2))
elif mode == 'verify':
    actual = json.loads(path.read_text())
    for key, value in expected.items():
        if actual.get(key) != value:
            raise SystemExit(f'Plan metadata mismatch: {key}')
    age = time.time() - actual['created_at']
    if not 0 <= age <= 4 * 60 * 60:
        raise SystemExit('Plan expired; rerun all jobs and review the new plan')
    print('Plan metadata verified')
else:
    raise SystemExit('Use create or verify')

23.6 Hạ tầng bucket lab

Tệp infra/envs/prod/main.tf

provider "aws" {
  region = var.aws_region
}

variable "aws_region" {
  type    = string
  default = "ap-southeast-1"
}

variable "bucket_name" {
  description = "Globally unique name for the lab bucket"
  type        = string
  validation {
    condition     = can(regex("^[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$", var.bucket_name))
    error_message = "Use 3 to 63 lowercase letters, digits or hyphens."
  }
}

resource "aws_s3_bucket" "lab" {
  bucket        = var.bucket_name
  force_destroy = false
  tags = {
    Environment = "prod-lab"
    ManagedBy   = "Terraform"
  }
}

resource "aws_s3_bucket_public_access_block" "lab" {
  bucket                  = aws_s3_bucket.lab.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_server_side_encryption_configuration" "lab" {
  bucket = aws_s3_bucket.lab.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}
